# Foundry Manual Validation

> Rewritten 2026-09-02. The previous version ran the pass against
> `docs/foundry-validation-fixtures/`, which are generated by
> `packages/foundry-exporter` — the fabricate-the-item path this project
> abandoned. **The module cannot consume those fixtures**, and they still
> target Foundry 13 and dnd5e 5.2.5. A pass run against them would have
> validated architecture that is not shipping. The legacy packet is still
> described at the end, as history.

## Goal

Validate the path the beta actually uses, inside live Foundry:

```
builder → ImportPayload → code → Worker (KV) → module → Plutonium → actor
```

This is the last seam with no automated guard. Every other layer has one; only
this one is checked by a human looking at a sheet.

## Setup

Verified environment — anything else and the results do not transfer:

- Foundry VTT **v14.367**
- `dnd5e` **5.3.3**
- Modules enabled: `bertinis-vault`, `plutonium`, `lib-wrapper`

**Confirm the installed module is the one you think it is.** Versions lie; a
copy four pull requests behind still called itself `0.2.2`. Compare hashes:

```
git hash-object "<FoundryData>/modules/bertinis-vault/src/import.js"
git rev-parse HEAD:apps/foundry-module/src/import.js
```

If they differ, copy `apps/foundry-module/{src,lang,styles,module.json}` over
the install and restart Foundry before starting.

Then run the automated gate, so a failure in the live pass is not something a
test would have caught:

```
corepack pnpm mvp:verify
```

## Getting a character to import

Publish a real build and take the code it prints:

```
cd apps/web
corepack pnpm exec vite build --ssr probes/rehearsal.ts --outDir .probe
node .probe/rehearsal.js
```

This exercises builder state, derivation, `ImportPayload` and `POST /builds` —
the same route a player takes. Codes live 90 days.

For shapes the probe does not cover, build the character in the Faro and use
the code the Ritual gives you. Cover at least: a martial with armour and a
shield, a prepared caster, a pact caster, a wizard with a spellbook, a
multiclass character, and one of each edition.

## What a correct import looks like

The point of referencing rather than fabricating is that the actor holds **real
compendium documents**. Check that, not just that items are present:

- `system.identifier` is populated on class, subclass, species and background
  (`harengon`, `drakewarden`, `hunters-mark`) — an empty identifier means a
  fabricated item.
- Spells carry a real `school` and **one or two `activities`**. An activity is
  what makes a spell rollable; a spell with none looks right and does nothing.
- Weapons carry a real `damage.base`.
- Icons are the real artwork, not the generic fallback.
- Sources are real (PHB, MPMM, FTD, BMT, TCoE, EGW, AAG).
- `ac.calc` is `"default"`, not a frozen number.
- `flags["bertinis-vault"]` carries `importedAt`, `rulesVersion` and
  `payloadVersion`.

## What has gone wrong before

Look for these specifically. Each was found on a real actor, and each is the
kind that leaves the sheet looking ordinary:

| Symptom | Why it matters |
| --- | --- |
| Class item without `ItemGrant` and `HitPoints` advancement | A ranger 5 with no Favored Enemy, no Extra Attack, no Fighting Style. Fixed 2026-08-31; confirm it stayed fixed |
| Equipment duplicated across editions | A 2014 character carrying both PHB'14 and PHB 2024 copies of a backpack, longbow, torch |
| Subclass features as one block of prose | Instead of citable items, and duplicated between the feat and the `subclass` item |
| An optional class feature granted unasked | A PHB'14 wizard receiving Cantrip Formulas (TCoE). Fixed in #65 |
| A warlock with no invocations | `optionalFeatures` dropped between layers. This is what the store-fidelity probe now guards |
| Quantities collapsed to one | Twenty arrows arriving as one arrow |

## The comparison that decides it

Compare the imported actor against **Rathma**, the character built by hand
through the Charactermancer. That is the known-good reference: it was *levelled
up*, so `dnd5e`'s own advancement system created its items.

An assembled actor and a levelled one differ in a way that matters — 312 fields
against 323 in the August comparison. Where they differ, the question is always
the same: is this something `advancement.apply()` would have done that the
module is skipping?

## What to capture

Record results in `docs/FOUNDRY-MANUAL-VALIDATION-REPORT.md`:

- the code imported, the character shape, and the edition;
- screenshots of the sheet, and of any warning the module showed;
- for each defect: what the sheet shows, what it should show, and whether the
  payload already had it right — that separates a builder bug from a module
  bug, and they have different owners.

## Exit condition

- Every shape above imports without a blocker.
- An item Foundry rejects is *named* rather than silently dropped.
- No fabricated documents: identifiers, activities and damage are real.
- Differences against Rathma are explained, not merely observed.

## The legacy packet, for history

`docs/foundry-validation-fixtures/`, `docs/FOUNDRY-VALIDATION-BASELINE.md` and
`docs/FOUNDRY-VALIDATION-MATRIX.md` describe the exporter-era validation: seven
fabricated-actor fixtures, five clean, one warning-only, one blocked. They are
regenerated by `corepack pnpm foundry:fixtures` and still exercise
`packages/foundry-exporter`, which is legacy. They are not part of this pass.
